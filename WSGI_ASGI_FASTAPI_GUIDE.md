# WSGI, ASGI, Django & FastAPI — How Python Web Servers Actually Work

A practical guide covering what happens when you run a Python web server, how
requests flow, where the event loop lives, and when to use sync vs async.

---

## 1. The two protocol standards

Python web applications talk to web servers through a **standard interface**. There
are two:

### WSGI (Web Server Gateway Interface) — PEP 3333 (2003)

The original standard. Synchronous, simple, battle-tested.

```python
# What a WSGI app looks like under the hood:
def application(environ, start_response):
    """
    environ:        dict with HTTP request data (method, path, headers, body)
    start_response: callback to set status + headers
    Returns:        iterable of bytes (the response body)
    """
    start_response("200 OK", [("Content-Type", "text/plain")])
    return [b"Hello, World!"]
```

**One function call per request. Blocking. Returns when done.**

Used by: Django, Flask, Bottle, Pyramid, and most pre-2018 Python web frameworks.

### ASGI (Asynchronous Server Gateway Interface) — 2018

The async successor. Handles HTTP, WebSocket, and long-lived connections.

```python
# What an ASGI app looks like under the hood:
async def application(scope, receive, send):
    """
    scope:   dict describing the connection (type, path, headers)
    receive: awaitable — call to get incoming data
    send:    awaitable — call to send outgoing data
    """
    await send({
        "type": "http.response.start",
        "status": 200,
        "headers": [[b"content-type", b"text/plain"]],
    })
    await send({
        "type": "http.response.body",
        "body": b"Hello, World!",
    })
```

**Awaitable. Non-blocking. Can handle many concurrent connections on one thread.**

Used by: FastAPI, Starlette, Django 3.0+ (with `asgi.py`), Quart, Sanic.

### Side-by-side comparison

| | WSGI | ASGI |
|---|---|---|
| Year | 2003 | 2018 |
| PEP | 3333 | Not a PEP (spec at asgi.readthedocs.io) |
| Paradigm | Synchronous | Asynchronous (asyncio) |
| Request handling | One thread per request | One event loop, many concurrent requests |
| WebSocket support | No | Yes |
| Streaming support | Limited (iterator) | Native (send chunks) |
| Server examples | gunicorn, uWSGI, mod_wsgi | uvicorn, daphne, hypercorn |
| Framework examples | Django, Flask | FastAPI, Starlette, Django 3.0+ |

## 2. How Django runs

### Development

```bash
python manage.py runserver
```

This starts Django's **built-in development server** — a simple, single-threaded
WSGI server. Never use in production.

### Production

```bash
# gunicorn with sync workers (most common)
gunicorn myproject.wsgi:application --workers 4 --bind 0.0.0.0:8000

# gunicorn with async workers (for Django 4.1+ async views)
gunicorn myproject.asgi:application -k uvicorn.workers.UvicornWorker --workers 4
```

### Django's process model

```
gunicorn --workers 4 myproject.wsgi:application

       gunicorn (master process)
            │
    ┌───────┼───────┬───────┐
    │       │       │       │
 Worker1  Worker2  Worker3  Worker4
 (sync)   (sync)   (sync)   (sync)
    │       │       │       │
  1 req   1 req   1 req   1 req   ← one request at a time per worker
```

- 4 workers = 4 simultaneous requests max
- Each worker is a **full OS process** with its own memory
- If a request blocks for 30 seconds, that worker is stuck for 30 seconds
- To handle more concurrent requests, add more workers (but each costs ~50-100 MB RAM)

### Django's WSGI file

```python
# myproject/wsgi.py (auto-generated by django-admin startproject)
import os
from django.core.wsgi import get_wsgi_application

os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'myproject.settings')
application = get_wsgi_application()
# ^ this is the WSGI callable that gunicorn imports
```

### Django's ASGI file (Django 3.0+)

```python
# myproject/asgi.py
import os
from django.core.asgi import get_asgi_application

os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'myproject.settings')
application = get_asgi_application()
# ^ this is the ASGI callable — used with uvicorn/daphne for async views
```

## 3. How FastAPI runs

### Development

```bash
# Simple — uvicorn directly
uvicorn api.app:app --reload --host localhost --port 8000

# With uv (your project uses this)
uv run uvicorn api.app:app --reload --host localhost --port 8000
```

`--reload` watches for file changes and auto-restarts (like Django's runserver).

### Production

```bash
# Option 1: uvicorn directly with multiple workers
uvicorn api.app:app --workers 4 --host 0.0.0.0 --port 8080

# Option 2: gunicorn as process manager + uvicorn workers (recommended)
gunicorn api.app:app -w 4 -k uvicorn.workers.UvicornWorker --bind 0.0.0.0:8080
```

Option 2 is preferred because gunicorn handles:
- Graceful worker restarts
- Auto-restart crashed workers
- Pre-fork process management
- Graceful shutdown on SIGTERM

### FastAPI's process model

```
uvicorn api.app:app --workers 4

       uvicorn (master)
            │
    ┌───────┼───────┬───────┐
    │       │       │       │
 Worker1  Worker2  Worker3  Worker4
 (async)  (async)  (async)  (async)
    │       │       │       │
  event   event   event   event
  loop    loop    loop    loop
    │       │       │       │
  + thread pool (40 threads each)
    │       │       │       │
 100s of  100s of 100s of  100s of  ← concurrent connections per worker
 conns    conns   conns    conns
```

Each worker can handle hundreds of concurrent connections because:
- The event loop handles async I/O without blocking
- A thread pool (default 40 threads) handles sync/blocking handlers
- So one worker ≈ 40 concurrent blocking requests OR hundreds of async requests

## 4. What happens when you type `uvicorn api.app:app`

Step by step:

```
uvicorn.main.run()
    │
    ▼
uvicorn.config.Config(app="api.app:app")
    │  Parses "api.app:app" into module="api.app", attr="app"
    │  Imports: from api.app import app
    ▼
uvicorn.server.Server(config)
    │
    ▼
asyncio.run(server.serve())          ← EVENT LOOP CREATED HERE
    │                                   (Python's standard asyncio loop)
    ▼
Inside serve():
    │
    ├─ await self.startup()
    │       │
    │       ├─ Open TCP socket on host:port
    │       ├─ Start listening for connections
    │       └─ Call your app's lifespan startup:
    │              your lifespan(app):
    │                  orc = Orchestrator("configs/app.toml")
    │                  app.state.orchestrator = orc
    │                  yield  ← startup complete, server ready
    │
    └─ Main loop: accept connections, dispatch to ASGI protocol handlers
         │
         ▼
    For each incoming HTTP request:
         │
         ├─ Parse raw TCP → HTTP request
         ├─ Build ASGI scope dict:
         │      scope = {
         │          "type": "http",
         │          "method": "GET",
         │          "path": "/health",
         │          "headers": [...],
         │      }
         ├─ Call: await app(scope, receive, send)
         │      │
         │      ▼
         │  FastAPI routing:
         │      path="/health" → @app.get("/health") → health()
         │      │
         │      ▼
         │  If handler is `async def`: run on event loop directly
         │  If handler is `def`: run in thread pool via asyncio.to_thread()
         │      │
         │      ▼
         │  Handler returns dict → FastAPI serializes to JSON
         │      │
         │      ▼
         │  Response sent back via `send()` → uvicorn writes to TCP socket
         │
         └─ Connection closed (or kept alive for HTTP/1.1 keep-alive)
```

## 5. Sync vs async handlers in FastAPI

FastAPI is unique: it supports BOTH sync and async handlers in the same app.

### How it decides

```python
# ASYNC handler — runs directly on the event loop
@app.get("/health")
async def health():
    return {"status": "ok"}

# SYNC handler — FastAPI auto-wraps in a thread
@app.post("/boardfarm/generate")
def generate(payload: CodegenJiraTestInputSchema):
    result = orc.codegen_app.generate(...)  # blocks for 30 seconds
    return {"generated_code": result}
```

FastAPI inspects the function at startup:
- `async def` → schedule on the event loop (`await handler()`)
- `def` → wrap in `asyncio.to_thread(handler)` → runs in the default thread pool

### When to use which

| Situation | Use | Why |
|---|---|---|
| Handler calls async I/O (`httpx.AsyncClient`, `asyncpg`, `aiofiles`) | `async def` | Direct event loop, no thread overhead |
| Handler does blocking I/O (sync DB, file reads, SDK calls like Anthropic) | `def` | FastAPI auto-threads it, event loop stays free |
| Handler is pure CPU (math, parsing, no I/O) | `def` | Thread pool handles it; event loop stays responsive |
| Handler mixes async AND blocking I/O | `async def` + `await asyncio.to_thread(blocking_fn)` | Run blocking parts in a thread manually |

### The critical mistake to avoid

```python
# ❌ WRONG — blocks the entire event loop for 30 seconds
# ALL other requests are frozen during this time
@app.post("/generate")
async def generate(payload):
    result = orc.codegen_app.generate(...)  # BLOCKING call in async handler!
    return {"generated_code": result}

# ✅ CORRECT — runs in thread pool, event loop stays free
@app.post("/generate")
def generate(payload):  # note: def, not async def
    result = orc.codegen_app.generate(...)
    return {"generated_code": result}

# ✅ ALSO CORRECT — explicitly thread the blocking call
@app.post("/generate")
async def generate(payload):
    result = await asyncio.to_thread(orc.codegen_app.generate, ...)
    return {"generated_code": result}
```

**Rule of thumb:** If your code uses `await`, use `async def`. If it doesn't,
use `def`. FastAPI handles the rest.

## 6. The event loop — what it actually is

An event loop is a **single-threaded scheduler for I/O operations**. It works like this:

```
Event Loop (single thread):
    ┌──────────────────────────────────────────┐
    │  time →                                  │
    │                                          │
    │  Request A: ████░░░░░░████  (await I/O)  │
    │  Request B:     ████░░░████              │
    │  Request C:         ████████             │
    │                                          │
    │  █ = CPU work (parsing, serializing)     │
    │  ░ = parked (awaiting network I/O)       │
    │      Other requests run during gaps      │
    └──────────────────────────────────────────┘
```

When Request A hits `await httpx.get("https://api.anthropic.com/...")`:
1. The event loop **parks** Request A (it's waiting for network I/O)
2. The event loop **picks up** Request B or C and runs their code
3. When the network response arrives for A, the event loop **resumes** A

This is why one thread can handle hundreds of concurrent async requests — most
of the time, handlers are waiting for I/O, not doing CPU work.

### Where the event loop is created

In uvicorn:
```
asyncio.run(server.serve())
```

`asyncio.run()` creates the event loop, runs `server.serve()` until it completes,
then closes the loop. This is Python 3.7+ standard library.

If `uvloop` is installed (`pip install uvloop`), uvicorn automatically uses it
instead. uvloop is a drop-in replacement for asyncio's event loop written in C
(Cython) — 2-4x faster for I/O-heavy workloads. No code changes needed.

## 7. Middleware — how it chains

Both Django and FastAPI support middleware, but the model differs:

### Django middleware (WSGI)

```python
# Wraps the view function — synchronous chain
class TimingMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        start = time.time()
        response = self.get_response(request)  # calls next middleware or view
        duration = time.time() - start
        response["X-Duration"] = str(duration)
        return response
```

Middleware chain:
```
Request → Middleware1 → Middleware2 → View → Middleware2 → Middleware1 → Response
```

### FastAPI/Starlette middleware (ASGI)

```python
# Wraps the ASGI app — async chain
@app.middleware("http")
async def timing_middleware(request: Request, call_next):
    start = time.time()
    response = await call_next(request)  # calls next middleware or route
    duration = time.time() - start
    response.headers["X-Duration"] = str(duration)
    return response
```

Same onion model, but async. Each layer can `await` the next.

## 8. Lifespan events — startup and shutdown

### Django: signals or AppConfig.ready()

```python
# myapp/apps.py
class MyAppConfig(AppConfig):
    def ready(self):
        # Runs once when Django starts
        import myapp.signals  # register signal handlers
```

### FastAPI: lifespan context manager

```python
# api/app.py — what your project uses
@asynccontextmanager
async def lifespan(app: FastAPI):
    # ── STARTUP ──
    orc = Orchestrator("configs/app.toml")
    app.state.orchestrator = orc
    yield
    # ── SHUTDOWN ──
    # cleanup hooks go here

app = FastAPI(lifespan=lifespan)
```

The `yield` is the key: everything before it runs at startup, everything after
runs at shutdown. The server only starts accepting requests after startup completes.

## 9. Dependency injection — FastAPI's killer feature

Django uses class-based views or function decorators. FastAPI uses `Depends()`:

```python
# Your project's pattern:
def get_orchestrator(request: Request) -> Orchestrator:
    return request.app.state.orchestrator

@router.post("/generate")
def generate(
    payload: CodegenJiraTestInputSchema,
    orc: Orchestrator = Depends(get_orchestrator),  # injected automatically
):
    result = orc.codegen_app.generate(...)
    return {"generated_code": result}
```

FastAPI resolves the dependency tree before calling the handler. Dependencies can
be `async def` or `def`, can depend on other dependencies, and can use `yield`
for cleanup (like DB session management).

Django equivalent would be middleware or a custom decorator:
```python
# Django — manual, no framework support for dependency graphs
@require_orchestrator
def generate(request, orc):
    ...
```

## 10. Deployment patterns

### Development (local)

```bash
# Django
python manage.py runserver 0.0.0.0:8000

# FastAPI
uvicorn api.app:app --reload --host 0.0.0.0 --port 8000
# or with your project's uv:
uv run uvicorn api.app:app --reload --host localhost
```

### Production (single machine)

```bash
# Django
gunicorn myproject.wsgi:application \
    --workers 4 \
    --bind 0.0.0.0:8000 \
    --timeout 120

# FastAPI (option A: uvicorn directly)
uvicorn api.app:app \
    --workers 4 \
    --host 0.0.0.0 \
    --port 8080

# FastAPI (option B: gunicorn + uvicorn workers — recommended)
gunicorn api.app:app \
    -w 4 \
    -k uvicorn.workers.UvicornWorker \
    --bind 0.0.0.0:8080 \
    --timeout 120
```

### Production (Docker) — your Dockerfile

```dockerfile
CMD ["uvicorn", "api.app:app", "--host", "0.0.0.0", "--port", "8080"]
```

### Production (behind nginx)

```nginx
# Same for both Django and FastAPI
upstream backend {
    server 127.0.0.1:8080;
}

server {
    listen 80;
    server_name myapp.example.com;

    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # For FastAPI WebSocket support (if needed):
    location /ws {
        proxy_pass http://backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

## 11. Worker types cheat sheet

| Server | Worker type | Protocol | Concurrency model |
|---|---|---|---|
| `gunicorn -k sync` | Sync | WSGI | 1 request per worker (process) |
| `gunicorn -k gthread` | Threaded | WSGI | N threads per worker |
| `gunicorn -k gevent` | Greenlet | WSGI | Cooperative multitasking (monkey-patched) |
| `gunicorn -k uvicorn.workers.UvicornWorker` | Async | ASGI | Event loop + thread pool per worker |
| `uvicorn --workers N` | Async | ASGI | Same as above, built-in multiprocessing |
| `daphne` | Async | ASGI | Twisted event loop |
| `hypercorn` | Async | ASGI | Supports HTTP/2 and HTTP/3 |

## 13. Mental model summary

```
                    Django (WSGI)                    FastAPI (ASGI)
                    ─────────────                    ──────────────
Entry point:        manage.py runserver              uvicorn api.app:app
Prod server:        gunicorn wsgi:app                gunicorn -k UvicornWorker
Protocol:           WSGI (sync)                      ASGI (async)
Event loop:         None (thread per request)        asyncio (one per worker)
Blocking handler:   Normal — worker is busy          Auto-threaded by FastAPI
Async handler:      Django 4.1+ only                 Native — async def
WebSocket:          Django Channels (add-on)         Built-in
Auto docs:          None (use drf-spectacular)        Built-in (/docs, /redoc)
Dependency inject:  Manual (middleware/decorators)    Depends() — framework-native
Serialization:      Django REST Framework             Pydantic (built-in)
```

The core insight: **Django was built for the synchronous web (2005). FastAPI was
built for the async web (2018).** Both work. Django has a much larger ecosystem
and ORM. FastAPI has better performance for I/O-heavy workloads and
auto-generated API docs. Your project uses FastAPI because the workload is
I/O-heavy (LLM API calls, search engine queries) and benefits from async
concurrency.
